# 儲存規則(三層儲存的責任與衝突處理)

> 與 `VERSIONING.md` 並列為資料層的兩條鐵律。改動任何一層的行為前先讀這份。2026-09-03 更新。

## 三層各管什麼

| 層 | 是什麼 | 責任 |
|---|---|---|
| 記憶體(store) | 正在編輯的個案 | 編輯中的唯一狀態;0.8 秒沒動作就寫回資料庫 |
| 瀏覽器資料庫(IndexedDB) | **真相來源** | 所有個案的正本;首頁清單、匯出、量表、時間軸都讀這裡 |
| 備份資料夾(File System Access) | **單向鏡像** | 內容真的變了才跟著寫一份 `case_<id>/case.json`;失敗只亮黃燈,不擋編輯 |

不支援資料夾 API 的瀏覽器(iPad Safari、Firefox)只有前兩層;備份靠「全備份」匯出檔與備份提醒。

## 規則(全部就這五條)

1. **資料庫永遠是真相。** 資料夾裡的檔案永遠不會自動覆蓋資料庫裡已有的個案。
2. **資料夾救援只補「資料庫沒有」的個案。** 換電腦、清掉瀏覽器資料、選回同一個資料夾時,缺的個案會被掃回來;已有的個案不會被自動改動。
3. **資料夾裡有較新的版本時,問使用者。** 啟動時與「選資料夾」時比對 `lastModifiedAt`;資料夾較新就用共用的確認框問:「用資料夾的版本」= 覆蓋這台的;「保留這台的版本」= 資料夾那份留著不動,會在下次真的編輯時被覆蓋(對話框講明)。同一個資料夾版本只問一次(`settings.folderNewerDecided`)。選資料夾時的順序固定是「先問,再把其餘個案寫出去」。
4. **開啟不算編輯。** 只是打開看一眼、`lastModifiedAt` 沒變:資料庫照寫(冪等),但不重寫資料夾、不計入備份提醒。個案一旦在本次開啟後寫過變動,之後一律鏡像(復原回開檔狀態也寫,兩邊才不會分岔)。實作:`services/saveSemantics.ts`。
5. **手動匯入才有完整的衝突對話框**(兩邊日期與人數、覆蓋 / 另存複本 / 略過)。

## 明說不做的事

- **不做雙向同步。** 這個工具不是同步軟體;備份資料夾放在 iCloud / Dropbox 可以,但兩台電腦同時編輯同一個個案,不會自動合併,只會依規則 3 問你要哪一邊。
- 對使用者的用詞一律是「**備份資料夾**」,不用「同步」——「同步」暗示雙向。

## 版本邊界

- 資料夾裡若出現本版讀不懂的新格式(`schemaVersion` 2.x)檔案:掃描時略過、且**不允許**本機的舊格式寫回去覆蓋它(`fileSystem.writeCaseJson` 會拒寫並亮黃燈)。
